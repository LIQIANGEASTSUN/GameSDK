## 实施要点

1. 按需求实现四组类型化通道，用字符串键定位通道，比较调用泛型参数的数量和有序 `Type` 身份，不走反射分发、`DynamicInvoke` 或每次发布的 `object[]`。先完成参数、回调输入、实例状态、重复和签名校验，再提交注册或绑定，上述检查失败保留原状态；发布的调用错误在逐监听捕获之外处理。回调调用列表校验仅在注册、注销入口进行，不要求 `Publish` 每次调用 `GetInvocationList`，其开销计入入口性能测量。
2. 候选存储为 `Dictionary<Action<...>, int>` 加带空槽的 `List`，四组通道使用对应委托类型。注册检查重复后追加，注销删除索引并立即将槽位置空；仅在通道发布深度为零时稳定压缩并重建索引，建议按失效数与存活数比例触发，避免每次注销全量搬移。哈希表、列表扩容与压缩成本及容量分配必须实测。
3. 每次发布固定本轮的 `List.Count` 上界，嵌套发布取其开始时的上界；逐次通过 `List` 索引读取，不缓存底层数组，以免回调扩容后仍读取旧存储。允许末尾追加使实际 Count 增长，本轮捕获上界不变；不得缩短 Count、移动既有槽位、调用活跃列表 `Clear` 或复用空槽。注销置空后，每次调用前复查实例状态和当前槽位。
4. 每条监听单独捕获异常并接真实日志；发布深度和延期整理统一在 `finally` 收尾。增加错误报告重入保护，报告自身抛错或重入引发的新报告不递归交回同一日志入口；按依赖契约使用独立兜底路径，不能因此跳过后续有效订阅。
5. 对接[普通类 Singleton](../../../Singleton/Docs/Tasks/实现普通类单例.md)的实际获取与生命周期钩子，依据其需求 AC-04、AC-05 核对释放完成和重入获取的判据，不另造单例。正常运行时释放后下一次获取按需新建，释放本身不创建实例。关闭时同步置失效、清空委托字典，并逐槽置空活跃列表以释放持有的回调引用，保留其 Count 与索引；只把活跃列表的 `Clear` 和容量维护延后到旧发布退出，绝不阻塞等待正在调用释放的 Publish。当前回调自然结束，旧 `finally` 只整理所属容器，不能清除新实例登记或监听。
6. 推荐先停止消费方消息入口和迟到回调，通过 `EventBus.Instance.Unsubscribe(...)` 完成成对注销，再释放总线。总线失效后，由所属实例完成残留监听清理，消费方不得为旧生命周期收尾再次获取 `Instance`；重新获取可能按单例契约惰性创建新实例，访问的是新生命周期。此顺序不需要新增公开 API。
7. 使用可信的 Unity 主线程入口建立校验，不能拿首次访问线程代替。按[模块状态](../状态.md)对齐连续 Play 的会话清理接线，不假定单例已有重置入口。核对上层、Hub 及 SDK 包内的直接单例入口，日志接入须符合 GameSDK 的依赖方向；接通后才将真实 API、用法、生命周期和验证入口写回模块 README。

## 必要验证

- 四组 API 的签名、全部 `void`、参数传递、显式配对、`null`、重复注册及键、未知事件、签名规则；验证规定的异常类型和上述校验失败后注册、绑定及原监听不变。
- 无参、1 参、2 参、3 参均验证注册、注销拒绝组合回调：通过 `+=` 或 `Delegate.Combine` 合并不同方法或两个相同方法，均抛 `ArgumentException`，不拆分、不创建签名、不部分修改监听。已有两个独立监听时，组合注销不会删除其中任一个；分别注册的多个监听各自接收、注销，逐回调异常隔离成立。
- 验证同对象同方法且同委托类型重新构造后可判重、配对，不同对象同方法互不注销，退订重订只留一份。覆盖合法 `Action` 逆变，注销保持原泛型参数和委托；以不同实际委托类型验证不误判相等。独立测试程序集使用共享 DTO，并覆盖同名不同类型、基类与派生类通道、反转参数顺序；负向编译输入隔离。
- 覆盖自身注销、注销后续监听、同轮注销重订、嵌套发布、最后一条注销及发布中释放；尤其验证回调追加监听触发 List 扩容后再注销尚未执行的监听。关闭同步使未执行监听失效、释放所持委托而不阻塞当前回调，Count/索引稳定；旧轮退出后完成容器整理，不误调或跳过有效监听。
- 多条监听连续抛错后其他监听仍接收，正常日志路径可观察且无聚合异常；模拟报告入口抛错、报告触发事件并再次出错，验证不递归报告、不阻断后续有效订阅，兜底行为符合日志契约。
- 用真实单例验证释放后未获取不重建、下一次获取产生干净实例，以及旧实例延期整理不影响新实例。验证旧 Subscribe/Publish 失败和旧 Unsubscribe 幂等清理，不重新积累监听；直接重新访问 `Instance` 可能进入新生命周期，推荐收尾顺序不额外创建实例。按最终会话清理接线，在真实连续 Play 和关闭 Domain Reload 场景验证旧监听隔离。
- 在同一负载与环境下测量发布、批量注册、批量注销、稳定增删及重入的耗时和 GC 分配，覆盖扩容和压缩边界；包含大量对象分别用同一个具名方法订阅的注册、注销负载，计入默认委托比较器及入口调用列表校验成本。记录容量、监听数、迭代次数及通过判据，Mono 与 IL2CPP 结论只覆盖实测环境，不预先承诺恒定成本或定制哈希。
- Unity 导入、编译、EditMode 测试与必要 PlayMode 生命周期验证默认由用户执行；Agent 提供测试代码、步骤和预期结果，并进行静态检查与独立审查。执行后记录实际结果，必要项未完成保持未完成状态并注明待用户验证。
